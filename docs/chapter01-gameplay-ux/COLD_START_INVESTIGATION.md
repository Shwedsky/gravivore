# Cold-start investigation

The owner's sustained first-session slowdown is treated as real. Its device cause is **not yet established**, and this delivery does not claim it is fixed. The APK includes actionable startup diagnostics rather than an unexplained loading delay or speculative shader warmup.

The focused Editor process observed the first 90 seconds of composition, initial ordinary population, first combat across the five farming areas, return to the hub, and a scene reload. It recorded two early frame stalls (532 ms and 228 ms), then no further frame above the 50 ms threshold during this observation. An earlier fresh-import graphics run recorded a 2,677 ms first-presentation stall; this is Editor evidence, not a phone measurement.

The focused run had 3,913 transforms, 932 renderers, 59 distinct shared materials, 20 particle systems and 13 audio sources at each inventory checkpoint. Live ordinary enemies fell from 20 to 16 during farming without growing the presentation hierarchy. Reload returned the same hierarchy/material/particle/audio counts. Twenty first-use ordinary visual creations took 0.11–1.09 ms each in this Editor run. Initial composition took roughly half a second; profile restore and HUD/map/presentation composition were the largest measured CPU groups. These results rule out duplicate composition and unbounded object growth in the tested flows, but do not establish the Android GPU/shader or asset-driver cause.

The batch Editor's Render Thread recorder was unavailable and its Main Thread recorder yielded zero. The report preserves those limitations explicitly; wall-clock frame timing and phase/creation timings remain useful. Device GPU/shader stalls require device evidence before selecting warmup assets or variants. ProfilerRecorder lifecycle follows the [Unity API documentation](https://docs.unity.com/en-us/engine/6000.7/script-reference/unity/profiling/profilerrecorder).

The DEV observer starts in Bootstrap before async Chapter loading, or before composition when a test directly loads Chapter 01. It records validation/full environment activation, profile restore/deserialization, HUD/player/material creation, fixed enemy pool, world geometry/gates, combat VFX/audio/repair, animation and map generation. Every startup frame is eligible, including the first five seconds. Stalls include phase, GC allocation/counter availability, enemy visual creation count, live enemies, repair activity and expanded map state.

Buffers are fixed: 128 significant stalls, 32 phase transitions, 128 enemy visual creation records and eight hierarchy snapshots. Inventories run at 1, 5, 15, 30, 60 and 90 seconds. Files are limited to `cold-start-current.json` and `cold-start-previous.json` under the application's reported persistent data directory. A restart retains the preceding session, allowing the failing launch and successful reopen to be compared. Pause/quit/lifecycle completion flushes evidence; recorders are disposed after 90 seconds. The existing separate bounded hitch diagnostics remain available for later-session issues. Release builds exclude the new observer and its visual-creation instrumentation.

The Android DEV log emits `[ColdStart] Bounded evidence: <actual path>`. If the issue recurs during the APK gate, collect both startup JSON files from that path and correlate the failing session's phase, wall-clock stalls, GC activity, creation timings and inventory changes with the successful reopen. A long graphics gap without corresponding creation/GC work calls for device graphics profiling; expensive initialization/creation groups call for narrowly targeted preloading. No balance, reward, save-schema or healing changes are part of that investigation.

Focused evidence: `verification/cold-start-focused-editor.json` and `verification/reload-focused-editor.json`. Full-suite evidence is kept separately because preceding tests may warm Editor caches.
